## 接入步骤

1. 复制根目录 .env.example 为 .env.local。
2. 保持 VITE_API_MODE=mock 可直接做学生端演示。
3. 后端确认 docs/openapi.json，先实现登录、退出两个接口。
4. 设置 VITE_API_MODE=remote，VITE_API_BASE_URL 指向接口根地址，如 http://localhost:8080/api/v1，重启前端。
5. 检查成功登录、密码错误、禁用账户、网络失败、超时、退出和非学生账号。
6. 按下面清单逐个把本地业务状态迁移到服务层。

默认地址 /api/v1 需要部署平台把该路径反向代理到后端。开发时可以直接配置完整后端地址；跨域服务应允许实际前端来源以及 Authorization、Content-Type 请求头和 OPTIONS 预检。当前采用 Bearer token，不发送跨域 Cookie。若团队改用 Cookie，需要共同修改契约、凭据和 CSRF 策略。

所有 VITE_ 变量都会进入浏览器，不能放数据库密码、服务私钥或 AI 服务密钥。

## 已实现的认证通道

接口返回直接 JSON，不包 data 外层。失败使用非 2xx 状态码，返回 code、message、可选 requestId。统一请求层处理 15 秒超时、网络失败、204 和错误信息，不自动重试写请求。

POST /auth/login

请求：
```json
{"schoolId":"学校ID","account":"20260001","password":"仅为示例"}
```

成功 200：
```json
{"user":{"id":"不透明用户ID","nickname":"公开昵称","schoolId":"学校ID","role":"student"},"accessToken":"服务端签发的令牌"}
```

身份由后端查询账户返回，前端不提交 role。后端必须校验密码、停用状态和权限。目前前端接收学生、心理教师和管理员身份，登录类别必须与返回身份一致。后端也应按当前发布范围限制登录。

失败示例 401：
```json
{"code":"INVALID_CREDENTIALS","message":"账号或密码不匹配","requestId":"请求追踪ID"}
```

POST /auth/logout

携带 Authorization: Bearer <accessToken>，成功返回 204 空响应；后端使会话或令牌失效。前端即使请求失败也清除本机状态，并提示服务端退出未确认。

GET /auth/me

携带 Authorization: Bearer <accessToken>。有效会话返回 200：`{"id":"真实用户ID","name":"显示名","role":"student"}`（教师为 teacher，管理员为 admin）；过期返回 401，停用或无权访问返回 403。此接口用于服务端会话校验，当前前端不自动恢复登录。

每次打开或刷新应用先显示登录页，不自动恢复上一次身份。登录成功后的会话与 Bearer 凭证仅在内存保留，不写入本地存储；启动会清除旧版本当前接口模式/地址的登录记录。学校绑定与外观偏好仍保留。退出清除本机会话；尚无自动刷新令牌和完整的业务请求会话过期跳转。/auth/me 可用于后续服务端会话校验，当前启动不请求该接口；现有业务仍为演示数据。

mock 模式允许学生 S-DEMO-01、教师 T-DEMO-01 和管理员 A-DEMO-01，密码 Demo@2026；remote 模式不会回退到本地校验，也不会显示演示凭据入口。

### APP 返回行为
前端统一通过 window.campusBack() 处理最上层页面：箭头、浏览器返回、Android 容器返回及左缘右滑使用相同路径。嵌套页面逐层返回，主页面保留访问来源和滚动位置；首页与登录页消费返回事件，保持应用打开。退出登录保留专门操作。未保存内容触发原有确认，确认框上的系统返回取消离开。Android 容器现有桥接接口可直接复用，仍需真机验证。

## 帖子举报与违规审核

学生帖子详情的举报会进入管理员「反馈处理 → 帖子举报与违规审核」队列。按帖子聚合举报，单账号单帖只能举报一次，累计 3 个不同账号的未处理举报标记为优先审核，不自动删除。管理员可筛选待审核、优先审核、全部公开帖、已删除，也可主动审核未被举报的公开帖。

保留或删除都必须填写审核说明并确认。保留会关闭现有举报，新的举报人可触发后续审核；删除会关闭举报并从共享帖子源屏蔽该帖，校园墙、热门推荐、搜索、地点分享、收藏及足迹列表均不再返回删除内容。已删除记录仅供管理员查看，保留原因、操作者、时间和帖子证据，不展示举报者身份。操作记录只写帖子编号及操作类型，正文与审核说明留在审核记录中。

共享状态由 CommunityProvider 维护：公开帖子、举报与审核记录在退出与切换身份后保留到刷新；非公开帖子仅作者可见且退出时清空，不进入管理员队列。当前仍为单次页面访问内的演示，刷新恢复样例，不支持跨设备或跨浏览器同步。

服务端接入需提供同校公开帖列表、举报创建与唯一约束（学校/帖子/举报者）、按帖子聚合的审核队列、带原因的审核写入与审计、删除屏蔽及证据保留。管理员写操作须检查当前有效角色、学校归属和帖子状态；举报次数仅为复核优先级。删除屏蔽须应用到所有查询与详情接口，服务端事务内关闭举报并记录审核及审计，不能仅由前端隐藏内容。

验证：npm run test:moderation 覆盖重复举报、阈值、跨校与角色限制、非公开帖子保护及删除后的状态；qa/check-post-moderation.mjs 使用 CDP 9350 与 dev 5190 验证举报、审核保留、删除确认、记录留痕、校园墙与搜索同步、刷新不复活、作者发布评论删除以及屏幕宽度。


## 统一校园身份入口（2026-10-13）

三种登录身份在登录前选择学校，认证后均落在校园首页，主导航固定为首页、发现、发布、消息、我的。TeacherArea 和 AdminArea 作为“我的”中的工作功能，以全屏侧页呈现，不再各自占用主导航。工作侧页不重复展示内部应用头和底部导航，拥有独立返回轨迹；返回校园不卸载公共内容区，草稿与个人资料保留。注销通过统一个人设置进行。

教师入口：心理支持工作台、预警中心、学生支持档案、咨询日程、教师服务设置。管理员入口：账号管理、开店授权、校园通知、反馈处理、帖子举报与违规审核、管理资料与操作记录。入口与工作侧页均检查认证身份，教师功能继续按 teacherId 限定负责范围；统一 UI 不授予其它角色的管理权限。

同校的三种有效身份均可读取公开帖、发布、评论、举报、购买并取消自己的订单、提交校园反馈及读取校园通知。学生开店管理仍需独立授权，教师和管理员不因公共订单能力获得商家操作权限。仅本人能访问自己的非公开帖子，管理员审核页仅收录校园公开帖；普通个人反馈页面仅展示本人反馈，管理员工作页可处理本校反馈。

反馈与订单现有内部字段 studentId / studentName 暂保留兼容，但对公共订单与校园反馈而言表示当前校园用户编号 / 名称，可能属于教师或管理员。服务端实现需按认证主体而非编号前缀或登录选项授权；角色专属接口和同校过滤必须保持独立校验。教师与管理员可以查看自己的私人会话，工作功能不能读取其他人的私人聊天。

SchoolGate 提供已认证学校上下文，个人中心显示登录学校及认证角色。主界面、登录、工作功能和弹层共用主题变量，工作页控件也跟随个人设置里的主题。

验证：qa/unified-campus.test.mjs 及 qa/moderation.test.mjs 验证角色边界、公共订单、私密内容隔离与举报；qa/check-unified-campus.mjs 验证三种身份的公共流程、专属入口、工作侧页返回、主题切换和 320/390/430/966px 布局。浏览器脚本使用 CDP [::1]:9351 与 dev 5191。

## 身份隐私与足迹（2026-10-13，替代旧绑定流程）

登录响应 nickname 只能是公开昵称；前端不再使用真实姓名作为显示名回退。Session.name 为兼容旧组件的公开昵称别名。Account 仅含昵称、内部用户 ID、学校、角色与状态，不能追加学生学号或真实姓名；管理员列表与反馈同样不返回这些字段。公开资料、帖子、评论、好友、闲置和活动只使用昵称与头像；联系人不展示用户编号。

IdentityProvider 将公开资料与私人校园身份分开。学号由已认证登录账号确定，个人编辑不能更改登录学号。本人可以查看自己的资料；只有同校、有效且实际负责该学生的教师可在授权档案中读取真实姓名、学号。管理员没有此权限。演示仅使用虚构身份，保存与权限检查在当前访问内有效；remote 认证不会加载演示私密身份。生产接入必须使用 /users/{id}/profile 的公开投影、/users/me/profile 的本人权限、/teacher/students/{id}/identity 的教师负责关系校验，禁止向普通客户端传递全部敏感数据再隐藏字段。真实姓名目前为学生填写信息，不能视为学校核验结果。

足迹入口可筛选浏览过、赞过、收藏过、评论过的帖子。评论过滤依据不透明 authorId，不能通过昵称判断同一人；删除或不可见帖子不再返回。正式后端实现本人交互历史接口，并按当前用户和学校过滤。公开 DTO 的内部 ID 用于关联操作，不得等于、编码或可推导学号。所有业务必须从认证会话获取学校，不得用本地存储或客户端传入的学校授权。

## 服务消息跳转示例（2026-10-14）

mock 模式的顶部铃铛新增一条评论、两条好友申请示例，均明确标注“示例”；remote 模式只保留现有校园通知，不展示这些虚构消息。ServiceMessages.tsx 的消息目标使用结构化字段：评论为 `{ type: 'post', postId: 'post-1' }`，好友申请为 `{ type: 'friend-requests' }`。按目标字段分发，不通过中文标题判断类型。

评论打开已有帖子详情及评论区；帖子已删除或对当前用户不可见时提示无法查看。好友申请打开 Messenger 的“新的朋友”页，可接受或忽略；两条示例均进入同一申请列表。目标页叠在服务消息之上，界面返回或手机返回都会回到消息列表，保留列表位置及本次已读标记。已读标记只在本次打开列表期间有效，不代表服务端已读状态。

后端接入时需返回消息 ID、标题、正文、时间、已读状态及结构化目标；列表、帖子访问与申请处理均须校验本人和学校权限，好友状态、已读状态由服务端提供。示例使用现有虚构帖子与申请，不代表收到真实消息。浏览器回归：`node qa/check-service-message-links.mjs`，默认预览 5173、隔离测试浏览器 9335，可通过 CAMPUS_QA_URL / CAMPUS_QA_CDP 覆盖。
